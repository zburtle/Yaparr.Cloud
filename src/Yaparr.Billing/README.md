# Yaparr billing (plug-in)

The payment side of Yaparr Cloud, as a plug-in for the server (see "Plug-ins" in the server's README): the Polar adapter, the webhook, the pay-first flow, the account page, and the payment controls in the admin portal. What a payment decides (who is covered, the `402`, `GET /v1/plan`) is in the server (`PlanGate`), which works without this.

Build it, and put `Yaparr.Billing.dll` in the folder that `PLUGINS_DIR` names. `deploy/docker-compose.billing.yml` and `deploy/billing.env.example` hold its settings.

- **Deleting an account** removes its subscriptions and billing id here. (Cancelling at the provider comes with the provider.)
- **The webhook** (`POST /billing/webhook/{provider}`, public): the raw body is checked by the provider's adapter (`400` for a bad signature or an old timestamp; at most 256 KB, `413` above); the same event is handled once (`billing_events`, kept 30 days); an event that names no subscription is `200` and nothing; then **the provider is asked what the subscription is now, and that is what is stored**, so the order events arrive in, repeats, and what each is called do not matter. A provider that cannot be asked answers `503` and the event is forgotten, so its retry is handled. The provider's name is in the address so that two can be live while moving from one to the other.
- **Reconciling** (every six hours, a minute after the service starts): every subscription that is not over and has not been heard of for three days, or whose period ended a day ago, is asked about again; a provider that cannot be reached or does not know it leaves it as it was. Events older than 30 days and unpaid sign-ups are cleared in the same run.
- **Paying first** (`POST /billing/start`, the website's form: `email`, `interval` = `monthly` or `yearly`): an address with no account gets one (no pass, no password) and a one-use token, and is sent to the provider's page with the account's random billing id as the reference. An address that already has an account (or a lifetime sign-up) is sent to sign in instead and nothing is started. **An address that has already paid is never sent to pay again, and its link is never replaced from outside**: with a password it is sent to sign in; without one (paid, and has not chosen a password yet) it is told to finish with the page it was sent back to, and a sign-up code is refused for it too. Someone who lost that page is given a new link by whoever runs the service: `accounts setup-link <email>` (it works once, for `PendingHours`, and the old link stops). Eight tries in a quarter of an hour from one address, then `429`. `GET /billing/done?t=…` is where the provider sends them back: once the payment is stored (or the provider says it has it) it goes on to the page that chooses a password, which says the payment has arrived and not "lifetime pass"; before that it looks again every two seconds (no script) and after fifteen looks says to come back to the same link. An account made this way that is never paid for, and whose token has run out, is removed.
- **The account page** (`/account/subscription`): the password is asked once, then a ticket (random, in memory, ten minutes) stands for it. It says where the account stands and offers **Go to payment** (monthly or yearly: the provider's page shows the price) and, once something is paid through a provider, **Manage payment and invoices** (the provider's portal, made fresh at each click). A lifetime account has no buttons; one that is already subscribed is not sent to pay a second time.
- **Deleting an account** (the account page, the admin portal) ends everything it pays for at the provider first, at once, and if a provider cannot be reached nothing is deleted. `accounts remove` has no provider to ask, so it says which subscriptions to cancel by hand.
- **Logging:** only what happened (`billing: webhook subscription (polar)`, `bad signature`, `the same event again`, `reconciled 3`), never an address, a reference, a token or a body; a test holds it to that.
- **Not done yet:** a provider (Polar), `accounts billing sync <email>` (it needs a provider, which only the running service has), and the state in the admin portal.
- **Polar** (`PolarBilling`, the only file that knows Polar's words). Make a Polar organization (the sandbox, <https://sandbox.polar.sh>, first), a product for each of monthly and yearly, an organization access token (scopes `checkouts:write`, `customer_sessions:write`, `subscriptions:read`, `subscriptions:write`) and a webhook endpoint at `https://<your service>/billing/webhook/polar` (format raw, API version `2026-10`) with the events `subscription.created`, `.updated`, `.active`, `.canceled`, `.uncanceled`, `.revoked`, `.past_due`, `customer.state_changed`, and **`refund.created` and `refund.updated`**. Then set, **in the environment and nowhere else** (they are secrets): `Service__Billing__Provider=polar`, `Service__Billing__Polar__AccessToken`, `Service__Billing__Polar__WebhookSecret` (the endpoint's `whsec_…`), and the product ids `Service__Billing__Polar__CloudMonthlyProduct` and `Service__Billing__Polar__CloudYearlyProduct`; `Service__Billing__Polar__Server` is `sandbox` or `production` (the default). With the compose file these are `BILLING_PROVIDER`, `POLAR_SERVER`, `POLAR_ACCESS_TOKEN`, `POLAR_WEBHOOK_SECRET`, `POLAR_CLOUD_MONTHLY_PRODUCT` and `POLAR_CLOUD_YEARLY_PRODUCT` in `.env` on the host (see `.env.example`). A half-set Polar stops the service starting and names what is missing. Calls pin Polar's API version (`Service__Billing__Polar__ApiVersion`, `2026-10`) so that a change by Polar is one we choose. The accounts are Polar's *external customer ids* (the random billing id, never an email address; the address is only given to Polar for the receipt). Webhooks are Standard Webhooks (id, timestamp and signature headers; five minutes of tolerance); both Polar's newer secrets and the older ones are accepted. A Polar subscription is `Active`, or `Canceling` when it is set to end with the period, `PastDue`, or `Ended` for anything else (cancelled, unpaid, incomplete, paused, or a state Polar adds later). Deleting an account revokes its subscriptions at once. **A refund ends the subscription**: Polar refunds the money and leaves the subscription running, so when a refund has gone through (not one that only corrects tax) the service revokes the subscription at Polar at once and then looks at it again. Refunding in Polar's dashboard is therefore all that has to be done; nothing has to be cancelled by hand. (Seen in Polar's sandbox: a refund alone leaves the subscription `active` and sends no subscription event.)
- **The sign-in page for the subscription** (`/account/subscription`) is the one place to send people to: it signs in (to see where the account stands, subscribe or renew, and manage payment and invoices) and, under *No account yet?*, starts a payment for an address that has none (the same form as `POST /billing/start`). The website and the direct-download app link to it; the Google Play build must not (see the design, *Android and Google Play*).
- **In the admin portal** (when billing is on): each account shows its plan (*Lifetime*, *Subscribed* with the renewal date, *Ending*, *Payment failing*, *Lapsed*, *Waiting for payment*, *Paid, no password yet*) and a *Payments* card counts them. Per account: *Give lifetime* / *Make it pay* (the pass), *New sign-in link* (for someone who paid and lost the page they were sent back to; shown once, and the old link stops), *Check payment* (asks the provider and stores its answer) and *End subscription* (at the end of the paid period, or now; asked first). With billing off none of this shows and none of the addresses exist.
